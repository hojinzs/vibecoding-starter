# 변경을 기록하고 올리기

커밋은 내 컴퓨터에 저장 지점을 남기는 일이고, push는 그 기록을 GitHub로 보내는 일이에요. **둘은 다른 단계**라서 따로 확인을 받아요.

## 1. 먼저 보여주기 (아직 아무것도 바꾸지 않음)

1. 프로젝트 폴더가 Git 저장소의 루트인지 확인해요. 상위 폴더 전체가 저장소면 **멈추고 알려줘요**.
2. Git 저장소가 아니면: 이 폴더에서 `main`을 기본 브랜치로 새로 만들지 물어봐요.
3. 커밋에 쓸 이름·이메일이 이 프로젝트에 설정돼 있는지 확인해요. 없으면 학습자에게 물어보고, 이메일을 공개하기 싫다면 GitHub의 noreply 이메일을 쓰는 방법을 알려줘요. 주소를 추측해서 만들지 마세요. 컴퓨터 전체 설정은 바꾸지 마세요.
4. `git status`로 바뀐 파일을 보여주고, 중요한 변경을 쉬운 말로 요약해요.
5. 다음이 섞여 있으면 **멈추고 알려줘요**.
   - `node_modules/`, `.next/`, `.env`, `.env.local` 같은 실제 환경 파일
   - 비밀번호·토큰·열쇠로 보이는 값 (값은 출력하지 말고 파일 경로와 종류만)
   - 이번 작업과 관계없어 보이는 변경
6. 커밋 메시지를 제안해요. 형식은 `feat:`(기능), `fix:`(고침), `docs:`(문서) 뒤에 한국어 한 줄이에요.

여기서 학습자의 확인을 기다려요.

## 2. 커밋하기

- 확인받은 파일만 `git add` 하고, `git diff --cached`로 실제로 들어갈 변경을 한 번 더 봐요.
- 커밋할 새 변경이 없으면 빈 커밋을 만들지 말고 그렇다고 알려줘요.
- 끝나면 커밋의 짧은 식별값과 메시지를 알려줘요.

## 3. push하기 (학습자가 원할 때만)

1. 계획을 먼저 보여줘요: 활성 GitHub 계정, 보낼 저장소(소유자/이름), 공개 범위, 브랜치, 보낼 커밋.
2. 원격 저장소가 없다면 **내 개인 계정의 private 저장소**로 만들 계획을 보여주고 확인을 받아요. public이나 조직 저장소로 임의로 만들지 마세요.
3. 확인을 받으면 push하고, **로컬과 GitHub의 최신 커밋이 같은지** 비교해서 알려줘요.
4. Vercel이 연결돼 있다면 `main`에 push하는 순간 배포가 시작된다는 것도 알려줘요.

## 절대 하지 않을 것

- `git push --force`, 기록 삭제, 제외된 파일 강제 추가
- 기존 remote를 덮어쓰거나 같은 이름의 저장소를 새로 만들기
- 오류가 났을 때 재시도부터 하기. 어디까지 성공했는지 먼저 알려줘요.
